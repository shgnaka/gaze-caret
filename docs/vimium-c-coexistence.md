# Vimium-C との共存と設定 JSON の変換

版: 0.1 / 作成日: 2026-09-05 / 状態: M1 / M2 の要件。実装・実機確認は未実施。

## 1. 製品として決めたこと

gaze-caret は独立した拡張機能として、通常の Vimium-C と共存する。Vimium-C を fork せず、改変版を配布せず、内部の関数を差し替える実装に依存しない。

Vimium-C 側の Caret / Visual 系のキーボード入口を設定で抑え、視線からのキャレット配置、その移動、最小限の選択範囲調整を gaze-caret が担当する。通常時のスクロール、リンク操作、タブ操作などは Vimium-C を使う。Vimium-C の Visual Mode の全コマンドを再実装することは必須にしない。

ここで「無効化」は、共存用の設定により対象のキーボード入口を使わなくすることを意味する。Vimium-C 内部から Caret / Visual のコードを削除することや、あらゆる外部呼び出しを禁止することは意味しない。

gaze-caret の設定画面に、ユーザーがエクスポートした Vimium-C の設定 JSON を入力として受け取り、gaze-caret の割り当てと競合する設定を調整し、Vimium-C に再インポートできる JSON をダウンロードする機能を置く。

## 2. 設定画面での操作

1. gaze-caret の開始・移動・選択・終了キーを設定する。通常時に使う開始キーと、gaze-caret のモード内だけで使うキーを分ける。
2. Vimium-C から書き出した JSON をファイル選択または貼り付けで読み込む。元ファイルは変更しない。
3. 対象の Vimium-C 版、OS、ブラウザと、解析できる範囲を表示する。元の JSON が既定値を省略している場合も、有効な既定キーを含めて調べる。
4. 競合するキー、Vimium-C 側のコマンド、モード、競合の理由、変更前後を表示する。確実に処理できる項目は変換案を生成する。必要なら gaze-caret のキーを変更するか、Vimium-C 側の該当割り当てを解除するかを選べる。
5. 変更後の設定をもう一度解析する。未解決項目がある場合は解決方法を示し、「競合解消済み」の設定として書き出せないようにする。
6. 変更内容を確認して JSON をダウンロードし、Vimium-C の設定画面でユーザーがインポートする。元の設定のバックアップも保持できるようにする。
7. 同時に動かして開始・移動・終了を確認する。Vimium-C 側を後で変更した場合は、再エクスポートした JSON で解析し直す。

他の拡張機能の保存領域を直接読み書きする方式にはしない。gaze-caret のキーを変えたり、別の JSON を読み込んだりしたら、古い変換案を無効にして再生成する。画面の「変換済み」はファイルを作れた状態であり、Vimium-C への適用済みや実機での競合なしを意味しない。

## 3. 共存の必須条件

| ID | 条件 |
| --- | --- |
| COEX-01 | Vimium-C の fork、改変版、内部関数の差し替えを採用しない。ユーザーは通常の Vimium-C と gaze-caret を別々に導入できる。 |
| COEX-02 | gaze-caret がキャレットの開始・移動・最小限の選択範囲調整・終了を持つ。キーは設定可能とし、文字・単語・表示行の移動、選択の開始と伸縮、解除・終了の受け入れ例を M1 で定める。Vimium-C の全 Visual 機能との同等性は要求しない。 |
| COEX-03 | 通常時は Vimium-C、gaze-caret のモード中は gaze-caret が担当キーを扱い、二重実行させない。モード外にまで `h/j/k/l` 等の通常操作を一律に無効化しない。入力欄、IME、他のモーダル操作、ブラウザ予約キーを区別する。 |
| COEX-04 | 共存設定では `enterVisualMode`、`enterVisualLineMode` およびその Caret 指定・別名・参照経由のキーボード入口を確認し、代替対象を無効にする。単に `c` や `v` という文字だけを削除して完了としない。解析不能な入口は CFG-07 の未解決項目にする。 |
| COEX-05 | 視線なし、古いデータ、対象 DOM なし、制御移譲の失敗では既存の Selection を保持し、通常状態を維持して理由を示す。無効化対象である Vimium-C の Caret / Visual を自動で起動する fallback は作らない。視線を使わない手動開始は別の明示操作として後で検討できる。 |
| COEX-06 | 制御の取得・終了・失敗時の復帰を設計する。通常終了、Esc、停止、タブ移動等で一時的なキー制御を解除する。遅い応答で別タブを変更しない。クラッシュ・拡張機能の無効化時にも復旧できる操作を用意し、元からの Vimium-C の除外・手動無効化状態を無断で上書きしない。 |
| COEX-07 | カメラ・推定・offscreen document は gaze-caret 自身が管理する。Vimium-C の offscreen document を流用しない。拡張機能境界を跨ぐのは必要な制御情報に限定し、画像・視線履歴・校正特徴量を渡さない。 |

起動キーを `v` または `c` にするのは設定の候補である。ユーザーの実際の割り当てを解析して決める。gaze-caret のキャレット移動中から選択モードへ切り替えても、視線から開始位置を毎回取り直さない。

## 4. JSON 変換の必須条件

| ID | 条件 |
| --- | --- |
| CFG-01 | Vimium-C のエクスポート JSON を検証して読み込む。name、environment、keyMappings の型を確認する。keyMappings の省略、文字列、文字列配列を区別し、改行・Unicode・エクスポーターの `$base64:` 表現を扱う。壊れた JSON や異なる形式は説明付きで拒否する。設定の文字列をコードとして実行しない。入力サイズ・ネスト・参照展開に上限を設ける。 |
| CFG-02 | 対応する Vimium-C の版と既定キーマップ、環境条件を互換プロファイルとして管理する。JSON に既定キーがないことを、キーが未使用である根拠にしない。版が不明・未対応なら確認が必要な状態にし、未検証の版で競合なしと断言しない。 |
| CFG-03 | keyMappings を構文として解析する。`map` / `map!`、`unmap` / `unmap!`、`unmapAll`、`mapKey`、複数キー列、モード、順序、条件、`run` / `runKey` / shortcut の参照を、対応範囲内で解決する。単なる全文文字列置換では処理しない。循環参照・動的な条件・未対応構文を診断できること。 |
| CFG-04 | 完全一致、接頭辞の衝突、キーの別名・変換先、対象モードと環境を含めて競合を検出する。ブラウザ拡張のグローバルショートカットや OS・ページ側の割り当ては、この JSON だけでは網羅できないことを表示する。 |
| CFG-05 | gaze-caret の予約キーと代替対象の入口について、該当する Vimium-C の割り当てを必要な範囲で調整する。既定キーが復活しないよう解除規則も含め、生成後に再解析する。全設定を `unmapAll` に置き換える処理や、通常時の移動キーの一律解除を標準にしない。 |
| CFG-06 | 変更対象以外の JSON の値、未知のフィールド、URL・検索設定・除外ルール等を保持する。keyMappings 内も関係のない行とコメントを維持する。外部コマンド方式に必要な extAllowList 等を変える場合は、追加する正確な拡張 ID と理由を差分に含め、既存の許可設定を保持する。 |
| CFG-07 | 変更箇所、根拠となる既定・ユーザー設定、無効になる操作、副作用、未解決項目を表示する。未対応構文を黙って削除しない。競合に影響する解析不能箇所が残るときは、自動変換を完了扱いにせず、キー変更や手動修正と再解析へ案内する。 |
| CFG-08 | Vimium-C が再インポートできる JSON と、必要なら別の変更レポートを明示操作で出力する。gaze-caret の設定スキーマで Vimium-C の JSON を包まない。元のファイルをそのままバックアップでき、同じ設定・互換プロファイルで再変換しても解除行が重複しない。 |
| CFG-09 | 読み込んだ設定は端末内で処理し、既定ではメモリだけに置く。自動アップロード、公開リポジトリへの追加、コンソールへの全文出力を行わない。通常の gaze-caret のキー設定の保存と、他拡張の設定ファイル全文の保存を区別する。 |

変換器の内部は、入力の正規化、構文解析、実効キーマップの構築、競合検出、変更案、JSON 出力に分けて TDD で育てる。解釈結果と元の行位置を対応づけ、画面で根拠を示せるようにする。

## 6. 実装方式と不確定要素

**設定変換は開始キー等の静的な競合を解消する機能であり、モード中の制御移譲は別に実装する。** `h/j/k/l` を設定から永久に取り除くと、gaze-caret を使っていないときの Vimium-C の操作も変わる。逆に、両方のイベントリスナーが動くまま、先に処理できた側が勝つ設計では二重実行を防げない。

| 方法 | 扱い |
| --- | --- |
| 設定変換で対象の起動キー・入口を解除 | 採用。通常時の競合を解消し、ユーザーの設定から個別に生成する。 |
| 外部コマンド等、Vimium-C が提供する経路で一時的にキー制御を譲る | 第一の検証候補。許可リスト、対象タブ・フレーム、開始と終了、既存状態の復帰を確認してから採用を決める。外部コマンドの受信だけを成功応答と取り違えない。 |
| 対象タブで Vimium-C を一時的に無効化し、終了時に戻す | 比較候補。一時的に Vimium-C の他機能も使えなくなる範囲、元の除外・強制状態、クラッシュ後の復旧が課題。 |
| ページの capture listener と stopImmediatePropagation だけで先取り | 単独の成立根拠にはしない。拡張機能の読込順等を変えた同時動作試験が必要。 |
| モード中専用の重複しない別キーを使う | 制御移譲が成立しない場合に提示する代案。通常の Vim 操作を維持できたことにはせず、操作の変更として評価する。 |
| Vimium-C の fork / 内部パッチ | 対象外。制御移譲が難しくてもこの方針へ切り替えない。 |

M0 の視線測定は主経路として続ける。一方、設定変換の純粋ロジックと、疑似座標を使う `spike/vimium-key-ownership` は、実際の視線精度に依存せず先に検証できる。共存の成立を M2 の最後まで未確認にしない。まず両拡張機能の通常操作・移動・終了・失敗復帰を、制限時間を決めた小さな spike で試す。

本人の Vimium-C JSON はまだ入力されていない。実装時は人工的な設定 fixture で TDD を進め、本人の設定に対する具体的な差分は、そのファイルを受け取った後に生成する。

## 7. 受け入れテスト計画

以下は将来の実装に対する計画であり、現時点でテスト済みとは扱わない。

| ID | 対応要件 | 先に作る受け入れ例 |
| --- | --- | --- |
| VC-01 | CFG-01, CFG-02 | 省略・文字列・配列・CRLF・日本語・$base64 の fixture を読み、同じ意味の実効設定になる。版不明・未対応を区別する。 |
| VC-02 | COEX-04, CFG-02, CFG-05 | keyMappings がない既定設定、v に別のコマンドがある設定、別キーからの Visual / Caret 起動で、対象の入口を調整する。削除後に既定の v / V / F8 が復活しない。 |
| VC-03 | CFG-03, CFG-05 | map! / unmap!、unmapAll とその後の map、複数定義・コメント・行継続を扱い、無効な解除や別モードへの意図しない変更を生成しない。 |
| VC-04 | CFG-03, CFG-04, CFG-07 | 単独キーと複数キー列の接頭辞、mapKey とモード、runKey・shortcut・条件分岐の参照を確認する。循環、展開上限、未対応条件では未解決理由を返す。 |
| VC-05 | CFG-06, CFG-08 | 無関係な JSON 値とマッピングを保存し、元ファイルを復元できる。同じ条件で 2 回変換しても意味と解除行が増えない。 |
| VC-06 | CFG-01, CFG-07 | 壊れた JSON、不正な型、巨大入力、過度なネスト、未知の影響する構文で、書き出し完了にせず理由を示す。次の正しい入力で再試行できる。 |
| VC-07 | CFG-07, CFG-08, CFG-09 | 設定画面の取り込み、差分、未解決項目、ダウンロードを確認する。入力ファイル・キー設定変更で古い変換案が無効になる。通信・保存・ログに設定全文が自動で残らない。 |
| VC-08 | COEX-01, COEX-02, COEX-03 | 通常版 Vimium-C と独立拡張を両方入れ、読込順を変える。通常時の j/k 等はスクロール、gaze-caret のモード中は移動・選択だけが起きる。入力欄・IME・既存のモーダル操作も確認する。 |
| VC-09 | COEX-05, COEX-06, COEX-07 | 移譲失敗、遅い応答、タブ移動、Esc、停止、拡張無効化を試す。既存選択を壊さず、キー制御を復旧でき、別タブや元の除外状態を誤変更しない。自前のカメラを停止できる。 |
| VC-10 | COEX-04, CFG-04, CFG-06, CFG-08 | 出力 JSON を対応版の Vimium-C に実際に取り込み、構文エラーがないこと、対象入口が無効なこと、その他の設定が保持されたことを確認する。ブラウザのグローバルショートカットは別に確認する。 |

VC-01〜VC-06 の純粋ロジックは Red → Green → Refactor で進める。VC-07〜VC-10 は制御できる境界のテストに加え、実際の拡張機能とブラウザの試験が必要である。既存の代表点選択の 17 件が成功しても、この共存機能の検証には数えない。
