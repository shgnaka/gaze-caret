# 開発方針: ブランチ、実験、TDD

作成日: 2026-09-05 / 対象: M0 の立ち上げから M2 まで

## 1. 採用するブランチ戦略

長期ブランチは `main` と `develop` の 2 本とする。`main` はリリースの基準、`develop` は次の版に向けた動作確認済みの統合先とし、作業は短いブランチと PR で進める。初期の README だけの `main` を、動作するリリースと解釈しない。

これは、このプロジェクト向けに手順を絞った運用である。ブランチの名前だけで品質は保証されないため、下記の統合条件とセットで扱う。

| 比較案 | 利点 | このプロジェクトでの負担・判断 |
| --- | --- | --- |
| GitHub Flow: `main` と短い作業ブランチ | 統合先が 1 つで管理が容易 | 研究中の統合版とリリースの基準をブランチで分けたい、という現在の希望に合いにくい。継続的に配布できる段階で再検討する。 |
| 完全な Gitflow | `develop`、リリース準備、公開版修正を分離できる | 複数の公開版を並行保守していない M0 では、常設する手順とマージ経路が多い。現時点では採用しない。 |
| `main` + `develop` + 短い作業ブランチ | 公開版と実験用の統合版を区別しながら小さく統合できる | **採用。** 2 本の同期が必要になる。機能ブランチを長期間ためず、リリース後に履歴をそろえる。 |
| Trunk-based development | 共通の統合先へ頻繁に反映でき、長期の分岐を避けやすい | `main` を直接この役割にする運用は今は見送る。小さな差分、頻繁な統合、必要時だけの機能切り替えは `develop` で実践する。 |
| 推定方式ごとに長期ブランチ | 初期の試作を隔離しやすい | UI・評価条件が分岐し、公平な比較と修正の共有が難しくなる。短い `spike/` と共通の評価器を使う。 |

比較の出典: [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)、[Gitflow の原提案と著者の追記](https://nvie.com/posts/a-successful-git-branching-model/)、[Trunk-based development](https://trunkbaseddevelopment.com/)。採否と適合性は、このプロジェクトの規模・不確実性・公開方針に基づく判断である。

## 2. ブランチの使い分け

| ブランチ | 分岐元 | PR の統合先 | 役割と寿命 |
| --- | --- | --- | --- |
| `main` | 初期ブランチ | — | リリースの基準。直接 push と force push を行わない。 |
| `develop` | `main` | リリース時だけ `main` | 次の版の統合先。自動検証に成功する状態を保つ。 |
| `feat/<topic>` | `develop` | `develop` | 観測可能な機能を 1 つ追加する。数日でレビューできる大きさを目安にする。 |
| `fix/<topic>` | `develop` | `develop` | 再現テストを先に追加し、不具合を直す。 |
| `docs/<topic>`、`chore/<topic>` | `develop` | `develop` | 文書、依存更新、開発環境。文書だけの変更に無意味なユニットテストを付けない。 |
| `spike/<question>` | `develop` | 必要な結論・再現手順を `develop` へ | 不確定な技術を調べる期限付き試作。製品コードとして採用する部分は、受け入れ例を定めてから機能 PR にする。 |
| `release/<version>` | `develop` | `main`、修正を `develop` にも反映 | 次版の開発とリリース準備を並行させる必要が出たときだけ作る。 |
| `hotfix/<topic>` | 公開済みの `main` | `main`、続いて `main` から `develop` | 公開版の緊急修正用。未公開の M0 では通常の `fix/` を使う。 |

既存の `requirements/mvp-spec` は `docs/` 相当として扱い、名前は維持する。PR #1 の統合先は `develop`。現時点で `main` へのマージは行わない。

PR は原則 1 つの目的に絞り、未完成なら Draft にする。依存 PR が未統合の場合は、その作業ブランチを一時的な base にした Draft PR を許容し、依存番号と最終的な統合先を本文に記す。親 PR を先に統合し、子 PR を `develop` に付け替えて差分・テストを再確認する。親子を一括で意図せず統合しない。

通常の機能 PR は squash merge を基本とする。依存 PR の親には merge commit を使い、子の祖先関係を保持する。親を squash した場合は、子を親の旧 head から `develop` へ rebase するか、子だけの変更を新しいブランチへ移す。共有ブランチの履歴を無断で書き換えない。

`develop` から `main` への昇格は **merge commit** で行い、squash で 2 本の共有履歴を切らない。昇格後は `main` を `develop` に取り込み、リリース修正や hotfix を取り残さない。リリース用タグは検証したコミットを指す。ブランチを削除しても、採用判断と再現用のコミットは PR・記録から追えるようにする。

## 3. 統合とリリースの条件

**`develop` への統合:** 対象要件と受け入れ例が明確、変更に必要な自動テストと型検査が成功、差分をレビュー済み、再現手順と制約を記録済みであること。ブラウザやカメラに触れる変更には該当する統合・手動確認を追加する。失敗中のテスト、無効化して隠したテスト、使う経路から切り離せない未完成機能は統合しない。統合後に壊れた場合は、原因を絞って修正するか該当 PR を revert し、統合先の成功状態を回復する。

**`main` への昇格:** 対象マイルストーンの配布物を再現でき、必要な自動検証と実機の基本動作確認が完了し、既知の制約・実測済みと未測定の項目が明記され、所有者がその版のリリースを決めたとき。M0 の実験アプリを alpha として配布することは可能だが、それを視線精度の実用成立や M1 への進行判定と同一視しない。今回は昇格しない。

CI は PR の base にかかわらず実行し、`develop` / `main` への push でも検証する。初期の純粋ロジックにはテストと型検査、Web アプリができた段階でブラウザテストと配布物のビルドを追加する。まだないビルドやカメラ測定を成功したチェックとして扱わない。機能フラグは、具体的な比較方式や未公開経路が必要になった時点で追加し、正式評価中には切り替えない。

GitHub の保護設定としては、両ブランチに PR 経由、force push と削除の禁止、CI 作成後の必須チェックを推奨する。チェック名は実際に成功したジョブを確認して登録する。1 人運用で自分の PR に他者の承認を必須にすると統合できないため、独立したレビュー担当がいる場合に承認数の必須化を行う。この文書は保護設定そのものを変更しない。

## 4. 実装の方法論

| 方法 | 採否と具体的な使い方 |
| --- | --- |
| リスクから先に検証する試作 | 採用。最大の不確定要素である視線の行精度・姿勢変化・遅延を M0 で測る。試作ごとに問い、固定条件、終了条件、結果と次の判断を残す。 |
| 機能を端から端まで薄く作る | 採用。疑似座標からキー確定・行表示・記録までをつなぎ、次に実カメラと学習器を接続する。UI、学習、拡張機能をそれぞれ完成させてから初めて接続する進め方を避ける。 |
| 受け入れテストから進める outside-in TDD | 採用。要件 ID とユーザーに見える結果から、1 つの受け入れ例を作る。カメラや DOM の境界を置き、必要な下位の振る舞いへ進む。 |
| 計算部分を小さく育てる inside-out TDD | 採用。中央値、時刻選択、回帰、距離、集計は、手計算できる入力と期待値で設計する。UI やカメラを起動せず検証できるようにする。 |
| 全依存を mock にする TDD | 標準にはしない。実装の呼び出し順を固定しやすい。時計・カメラ・検出器など外部の境界だけを制御し、内部の計算と連携は実物を使う。 |
| 一括実装後にテストを足す | 通常の機能・修正には採用しない。調査用の使い捨て試作は可能だが、製品へ採用する前に受け入れ例を定義して TDD で組み込む。 |

TDD の基本は、失敗する振る舞いのテスト、成功させる最小の変更、成功を維持した整理の順である。[Martin Fowler による説明](https://martinfowler.com/bliki/TestDrivenDevelopment.html)

最初から大きな汎用基盤や複数のパッケージに分割しない。単一リポジトリ内で、純粋な計算、カメラ・検出器の adapter、画面の処理を分ける。共通の推定結果契約は維持し、別エンジンの必要が出た時点で置き換え点を増やす。既存の [要件](requirements.md) と [検証計画](validation-plan.md) を仕様の基準にする。

## 5. TDD と視線実験の 2 つのループ

| 自動テストで固定すること | 本人の実験で判断すること |
| --- | --- |
| 既知データに対する回帰、座標変換、中央値、行距離が定義どおりか | 未知の注視位置でどれだけ誤るか |
| 古い・押下後の結果を使わず、停止後に復活させないか | 自然な読書、姿勢変更、眼鏡、時間経過に耐えるか |
| 評価中に学習せず、失敗も分母へ入れるか | 校正・修正も含めて選択操作が楽になるか |
| 指定した設定とデータを再現して集計できるか | CPU 負荷、電池消費、実効頻度が許容できるか |

テストの期待値を、検証対象の関数を呼んで生成しない。学習と評価のデータは分ける。良い実測値へ合わせてテストを書き換えず、仕様を変える場合は変更理由と新しい受け入れ例を先に記録する。網羅率だけを品質や視線精度の証明にしない。

研究では、まず 1 つの条件を変えて同じ評価器で比較する。モデル、特徴量、平滑化などの方式名に加え、コミット、設定、モデル資産の版、seed、学習・評価セッションを記録する。実験データや本人の特徴量を公開リポジトリへ自動追加しない。人工データの fixture と、共有を選んだ集計結果を区別する。
