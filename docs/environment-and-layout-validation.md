# カメラ配置と複雑なページの検証要件

版: 0.1 / 作成日: 2026-09-05 / 状態: 要件・受け入れ計画。実装と実測は未完了。

[基本要件](requirements.md) と [検証計画](validation-plan.md) を拡張する。最初の実験は、固定したカメラと 1 段組・複数段落の文章で行う。その基準を残し、カメラ配置への適応と、実際のページに近い条件を段階的に調べる。Vimium-C を fork しない方針、TDD、`develop` への PR 運用を引き継ぐ。

## 1. 検証する問いと段階

| 問い | 切り分ける条件 | 実施段階 |
| --- | --- | --- |
| カメラの設置位置が違っても利用を開始できるか | 画面に対する位置・向きと、配置ごとの校正 | M0 で確認フェーズを試作し、M2 の拡張機能に組み込む |
| 校正後の自然な動きに耐えられるか | カメラを固定したままの頭の向き・距離、照明、時間経過 | M0 の基準測定から始め、複数配置へ評価を広げる |
| 複雑なページで目的の文章を選べるか | 視線座標の誤差と、座標から DOM の行・領域を選ぶ誤り | M0 の既知 fixture を段階的に増やし、汎用 DOM・選択は M1、両拡張の共存は M2 |

カメラの設置確認と精度の校正は別の仕事である。MediaPipe の顔変換行列は標準の顔モデルから検出した顔への変換であり、画面に対する物理的なカメラ位置を直接出力するものではない。[公式資料](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)

このため初期設計では、本人による大まかな配置確認と、画面上の既知の点を見る校正を組み合わせる。顔の向きだけから、カメラ移動と頭の移動を確実に区別できるとは仮定しない。

## 2. カメラ位置の確認と環境への適応

| ID | 必須条件 |
| --- | --- |
| ENV-01 | 明示的なカメラ開始後、使用カメラ、対象画面、画面に対するカメラの大まかな位置を確認する。上・下・左・右・その他の位置を入力でき、不明も表現できる。左右のずれ、傾き、距離の補足は任意とし、正確な cm や角度の入力を必須にしない。M0 で試作し、M2 の拡張機能にも確認フェーズを設ける。 |
| ENV-02 | 校正前のプレビューで顔・両目の検出状況を確認し、閉眼、見切れ、暗さや反射の疑いについて修正できる案内を出す。自動判定できない状態は本人の確認で補う。反転プレビューと推定入力の座標規約を一貫させ、検出成功を精度保証と表示しない。正式評価中は顔プレビューと視線の点を隠す。 |
| ENV-03 | 同じデバイスでも物理配置を変えた場合は、確認のやり直し、古い履歴の破棄、再校正を要求する。「カメラ・画面の位置を変えた」の明示操作を用意する。配置、カメラの取得設定・切り出し、対象表示領域の変更をモデルの適用条件に含める。変化の自動検知は補助として扱い、未確認の旧モデルを黙って再利用しない。 |
| ENV-04 | 初期の個人用 CPU 回帰を基準として、目に対する虹彩の相対位置、顔の向き・位置・大きさの特徴量と正規化を比較する。配置ごとの再校正で吸収できる差と、同じ配置での姿勢変化への耐性を別々に測る。特徴量や閾値を変えたモデルは別の版として評価する。 |
| ENV-05 | 校正直後、固定配置での姿勢・距離・時間の変化、配置を変えて再校正した場合を別条件にする。開発用の調整と最終評価をセッション単位で分離する。未知の配置への一般化を主張する場合は、配置ごと保留した評価を追加し、無校正での適用と再校正後の性能を混ぜない。 |
| ENV-06 | 配置・環境・モデル条件を、個人情報を含まない識別子と数値・分類で結果に対応づける。条件別の座標誤差、行一致、候補なし、中断、校正時間・取り直し回数を報告する。撮影画像、映像、音声、永続的な deviceId は保存・出力しない。未実施の配置や人数を明記する。 |

確認フェーズは、カメラ開始 → 配置と写り方の確認 → 校正 → 学習に使わない点での検証という順にする。「配置未確認」と「校正が必要」を区別する。不明な物理寸法を推定値として埋めず、不明のまま本人が配置を確認したセッションとして扱えるようにする。

カメラがディスプレイ上部に付いていても、ウィンドウの位置、ノート PC のふたの角度、外付けカメラの向きが変われば、目・カメラ・対象表示領域の関係は変わる。通常の姿勢変化をすべて再校正要求にせず、品質の低下や利用者による再確認から校正し直せるようにする。姿勢変化が検出できない場合もあるため、短い独立検証での確認を残す。

### データと状態の境界

- `placementId` と `placementRevision` はアプリ内で作る識別子と更新番号とする。大まかな位置、本人が確認したか、映像の実際の寸法、前処理の版、対象画面・表示領域の記録を対応づける。物理寸法や角度を記録する場合は、本人入力・計測・推定の由来を区別する。
- `contextId` に配置の更新を含め、モデルに校正時の条件を持たせる。機器の識別子が同じでも、配置の変更で以前の校正を適用不可にする。以前の文脈で取得し、変更後に到着した非同期結果を捨てる。
- 文書のスクロールや文字の再配置は、カメラの物理配置変更とは分ける。表示領域が同じなら、履歴と DOM の幾何情報を更新し、回帰モデルまで無条件に捨てない。ウィンドウ位置・寸法・倍率の変更は従来どおり再校正の対象とする。
- 明示的な書き出しだけを認める既存のデータ方針を維持する。M0 の標準はメモリ内の保持であり、配置情報を追加したことをモデルの自動保存・再読込の根拠にしない。

### ロバスト化を判断する実験

| 比較 | 固定するもの・変えるもの | 結果の意味 |
| --- | --- | --- |
| 配置別の適応 | 手元で実現できる配置を選び、配置ごとに再校正。文章と評価手順をそろえる | その配置で校正した利用者に対応できるか |
| 同じ配置での変化 | 校正・モデルを固定し、自然な頭の向き、距離、照明、時間を個別に変える | 利用中の許容範囲と再校正の負担 |
| 未使用セッション | 開発時と別の収集回を用い、その回の校正データと評価データも分離 | 同じ本人・配置で結果を再現できるか |
| 未使用配置 | 開発・モデル選択に使わない配置を丸ごと保留する | 配置を跨ぐ一般化。配置ごとの再校正を許す評価とは分ける |

最初は手元で可能な基準配置と異なる配置を比較する。固定カメラしかなく変更できない条件は未実施と記録し、追加機材の購入を前提にしない。複数人への対応は別の人数・分割計画を要し、本人 1 人の結果から保証しない。

連続フレームを無作為に分けて同一収集回を学習・最終評価へ混在させない。標準化、特徴量選択、正則化、品質閾値の調整も開発用データだけで行う。自然な使用での顔・照明などの変動と、異なるデータ条件への一般化は既存研究でも課題として扱われているが、その論文の性能値を本実装へ流用しない。[MPIIGaze 原論文](https://arxiv.org/abs/1504.02863)

未知配置へ旧モデルを適用する診断を行う場合は、明示的な実験条件として隔離する。通常操作で ENV-03 の再校正要求を迂回する機能にはしない。単純な画像の平行移動・回転に元の視線ラベルを付けても、物理的なカメラ移設と同じ教師データになるとは仮定しない。まず実際の配置と正解点を対応づけたデータで比較し、画像モデル全体の再学習や GPU の導入は初期の必須条件に加えない。

## 3. 複雑なページを再現する実験

| レベル | 再現するページ・CSS | 主な確認事項 |
| --- | --- | --- |
| L0: 基準 | 日本語横書き、1 段組・複数段落、固定の文字サイズと行間 | 最初の座標・行評価。既存の 20 / 60 試行を維持する |
| L1: 静的な複雑さ | 本文とサイドバー、複数段組、Grid / Flex のカード、見出し、箇条書き、コード、表、混在する文字サイズ・行間 | 同じ高さにある別領域、DOM 順と表示順の違い、折り返しと行の分割 |
| L2: 位置が変化するページ | sticky / fixed ヘッダー、重なるパネル、overflow の切り抜き、内部とページのスクロール、遅延画像・フォントによる再配置、CSS の平行移動・拡縮 | 隠れた文字の除外、現在の位置への更新、変更中の中断、古い座標の排除 |
| L3: 利用場面の再現 | 目次付き技術文書、記事と関連記事、フィードとコメント、商品カードなどを自作文章・合成データで再現 | 典型的なページ構成を組み合わせた評価と、M1 の選択・修正操作 |

L0 を最初の実験として完成させ、L1〜L3 を独立した条件として順に追加する。M0 では正解と対象 DOM が分かるローカル fixture を使う。任意のサイトを探索してキャレットを置く機能は M1、実際の利用ページと Vimium-C の共存確認は M2 に対応づける。複雑な全条件の完了を、最初の L0 測定を始める前提にしない。

| ID | 必須条件 |
| --- | --- |
| LAY-01 | L0 の基準を残し、L1〜L3 の段階的な fixture 群を作る。各 fixture に版、目的、対象とする CSS 条件、期待する対象領域を定義する。実サイト風の構成は自作の文章・データで再現し、実際の閲覧ページを無断収集しない。 |
| LAY-02 | 文字範囲の矩形断片から行・ブロック・段または表示領域を扱う。要素全体を囲む 1 個の矩形を、段間や空白まで文字であるかのように扱わない。切り抜き・重なり・画面外を考慮し、確認できない可視範囲を有効な候補として保証しない。 |
| LAY-03 | fixture、表示領域、フォント、スクロール位置、レイアウト更新を識別する。位置が変わったら矩形を取り直し、古い履歴・候補・遅れて返る処理を使わない。変更中の試行は理由付きの中断として残す。 |
| LAY-04 | 既知の座標から正しい DOM 領域を選べることを、カメラなしの自動テストで先に検証する。その後、実視線を使う評価を行い、座標推定の誤差と候補選択の誤りを分けて報告する。正解 DOM・目標ラベルは評価器だけが持つ。 |
| LAY-05 | ページ群・配置・モデルごとに誤差と全試行の成否を集計する。隣接行は同じ論理ブロックかつ同じ段・表示領域内で定義し、横のサイドバーを隣接行の成功に含めない。別領域の選択も識別する。 |
| LAY-06 | 対応する通常 DOM、未対応構造、利用できないページを区別し、未対応では理由を出して既存選択を保つ。iframe、Shadow DOM、縦書き、Canvas、画像、PDF、ブラウザ内部ページを今回の対応済み条件に加えない。任意の回転・3D 変形も初期の対応保証から外す。 |

`Range.getClientRects()` は文字範囲の矩形断片を返し、CSS transform も反映する一方、返された矩形は後の変化へ自動追従しない。仕様上の内容順も、複雑なページの見た目の読み順とは同一視できないため、これを出発点に行・領域を組み立てて再配置時に更新する。[CSSOM View の Range 定義](https://drafts.csswg.org/cssom-view/#dom-range-getclientrects)

`elementFromPoint()` だけであらゆる重なりを解決できるとは仮定しない。たとえば `pointer-events: none` の要素はヒットテストの対象から外れる。既知 fixture で可視性を検証し、扱えない構造は候補なしとして理由を残す。[CSSOM View のヒットテスト](https://drafts.csswg.org/cssom-view/#dom-document-elementfrompoint)

### 再現用のデータと集計

fixture の正解には、`fixtureId` / `fixtureVersion`、対象ノードの別名、文字範囲の offset、`blockId`、`regionId`、行の識別子を持たせる。実行環境には CSS viewport 寸法、DPR、ブラウザ・フォントの版、各スクロール領域の位置、設定 seed、`layoutRevision` を記録する。DPR だけでページズームと OS 倍率を識別せず、既存の環境記録を併用する。

`layoutRevision` は校正の `contextId` / `modelId` と別に管理する。取得からキー確定までの途中でレイアウトが変わった結果は適用しない。フォントや画像の読み込みで目標が移動した場合は試行を中断し、新しい trialId で提示し直す。正解を新しい位置へ黙って差し替えて過去の決定を採点しない。

L0 の 6 区分は維持する。複雑な fixture では段落に相当する論理 `blockId` を定義し、隣接行の条件に同じ `regionId` を加える。同じブロックでも別領域なら「同じ段落のそれ以外の行」に分類し、別ブロックなら「別段落」に分類する。全試行を相互排他的な 6 区分へ入れ、合計を一致させる。別領域を選んだかは追加の属性として併記し、7 番目の排他的な区分として足さない。定義の版をデータに含め、L0 と複雑な条件を混ぜた正答率だけで性能を示さない。

M1 のキャレット・選択試験では、行評価に加えて実際の DOM Range、選択範囲、修正キー数と選択完了時間を測る。既知座標で DOM が正しく選べたことは、本人の視線精度や利用上の使いやすさの証明にはしない。

## 4. TDD の受け入れ例と実機確認

以下は実装前にテストへ落とす計画であり、現時点の成功済みテストではない。純粋な状態遷移・データ分割・集計は小さな入力から Red → Green → Refactor で進める。矩形・スクロール・選択の検証には、実ブラウザで描画した fixture を使う。期待値は仕様と独立した固定例から定め、検証対象の候補選択関数から生成しない。

| ID | 対応要件 | 観測する結果 |
| --- | --- | --- |
| EV-01 | ENV-01, ENV-02 | 開始前に映像を要求せず、開始後は配置未確認・校正必要を区別する。不明な物理寸法を許し、目が見切れた状態で校正を成功扱いにしない。正式評価ではプレビューが消える。 |
| EV-02 | ENV-03 | 同じ deviceId で「配置を変えた」を選んでもモデルを適用不可にする。校正を要求し、旧文脈の履歴・遅延結果が復活しない。文書スクロールだけの場合は校正を保持する。 |
| EV-03 | ENV-02, ENV-04 | 既知の特徴点と異なる画像寸法・反転規約を使い、相対位置の期待値を確認する。欠損を有効値に変換せず、前処理の版違いのモデルを拒否する。 |
| EV-04 | ENV-05 | 収集回・配置を指定した人工データで分割を検証し、保留データが標準化・モデル選択・閾値調整へ混入しないことを確認する。 |
| EV-05 | ENV-06 | 配置ごとの成功・失敗・中断と校正負担を再集計できる。不明値と 0、未実施と失敗を区別し、禁止された画像・永続 ID を出力しない。 |
| LV-01 | LAY-01, LAY-02, LAY-04 | 2 段の同じ高さの文章、段間の余白、DOM 順と表示順が異なる固定例で、既知の座標から期待する領域を選ぶ。正解ラベルだけを変更しても候補は変わらない。 |
| LV-02 | LAY-02 | 折り返しと混在する文字サイズ、CSS 拡縮で矩形断片が更新される。要素の大きな外接矩形だけで空白を文字候補にしない。 |
| LV-03 | LAY-02, LAY-06 | sticky / fixed 要素の下、切り抜かれた部分、画面外、pointer-events: none の重なりを含む fixture で、隠れた文字を選ばない。未対応なら理由付きで既存選択を保持する。 |
| LV-04 | LAY-03 | 内部スクロールと文書スクロール、フォント・画像による再配置で旧候補を破棄する。変更前に開始した処理を変更後に適用せず、中断を記録する。 |
| LV-05 | LAY-04, LAY-05 | 既知の誤選択集合で 6 区分の合計が全試行数に一致し、別段・別サイドバーが隣接行の成功に紛れない。座標誤差と別領域の選択を区別する。 |
| LV-06 | LAY-01, LAY-03, LAY-06 | fixture の版・viewport・スクロール・layoutRevision を復元できる。未対応構造では選択を壊さず、通常 DOM の結果と混ぜて対応済みと表示しない。 |

本人の実機では、ENV-01〜ENV-06 について配置確認・再配置後の再校正を行い、配置別と姿勢変化後の精度・失敗・校正負担を記録する。LAY-01〜LAY-06 について、L0 と追加した各ページ群を別々に実測し、M1 では修正操作まで確認する。実行できなかった配置・ページ群・ブラウザは未実施として残す。本人の実験データは公開リポジトリへ自動追加しない。

## 5. 完了の扱い

カメラ確認の試作と状態管理は M0 の受け入れ条件へ組み込む。複数配置のロバスト性評価と L1〜L3 の fixture は、その後に進める拡張検証として追跡する。最初の L0 測定、複数配置での性能確認、複雑な DOM での選択成立、M2 の拡張 UI への組み込みを、それぞれ別の完了として記録する。

テストと測定がそろうまでは「配置に依存しない」「任意のページで使える」とは結論づけない。測定により支持される範囲、再校正が必要な条件、候補なしとする条件を結果として残す。
