# 最初の TDD: 押下前の代表点選択

実施日: 2026-09-05 / 対象: POS-02 / POS-03、A-09 の一部

## 作ったもの

`src/core/select-gaze-point.ts` の `selectGazePoint` は、キー押下時に渡したサンプル集合から代表点か位置なし理由を同期的に返す。カメラ、DOM、学習器、時計の実物に依存せず、入力と出力だけをテストできる最初の単位である。

このスライスで履歴ストアは実装しない。60 件 / 1,000 ms の保存上限、同じフレームの重複排除、停止・スクロール等での履歴破棄、実際のキー処理との接続は、次のスライスで実装・検証する。A-09 全体、M0、実機の視線精度は未完了である。

## API の前提と結果

呼び出し側は、キー処理開始時に **受信済みで、同じフレームの重複がないスナップショット** を渡す。`sampledAt`、`producedAt`、`pressedAt` は同じ単調時計で表し、x / y は同じ表示領域の CSS px とする。Worker などへ分離した際は、そこでの推論完了が受信時刻と同じとは限らない。後から受信した結果を古いスナップショットへ追加して再決定しない。

初期設定は [検証計画](validation-plan.md) の押下前 250〜50 ms、両端を含む時間窓、3 件以上、座標ごとの中央値、各軸の MAD が 40 CSS px 以下である。設定は明示的に差し替えられる。顔検出器の confidence は使わず、行に当たる確率も出力しない。

`producedAt <= pressedAt` に加え、有効な有限座標・正常な時刻・現在の contextId / modelId に属する結果だけを選ぶ。`sampledAt` が時間窓の外の値は加えない。無効サンプルの座標を 0 で補完しない。入力集合を変更せず、返却後に呼び出し側の履歴が変わっても決定を変更しない。

| reason | 意味・優先順 |
| --- | --- |
| `invalid-context` | 現在の文脈またはモデル ID がない。あるいは、押下までに利用可能な有効データがすべて別の文脈・モデルに属する。 |
| `stale-data` | 現在の文脈・モデルで使えるデータはあるが、すべて時間窓の開始より古い。窓を広げない。 |
| `insufficient-samples` | その他の件数不足。履歴なし、無効値だけ、時間窓より新しい値だけ、押下後の結果だけなども含む。 |
| `excessive-spread` | 必要な件数はあるが、いずれかの軸の MAD が閾値を超える。 |
| `null` | 代表点を返せた。実際の注視点との一致を保証する値ではない。 |

結果の sampleCount と最新・最古のサンプルの古さは、時間窓内で選んだ集合についての値である。集合が空なら古さは null。件数不足なら MAD は null、分散過大なら計算した MAD を返す。位置なしでは point は null。呼び出し時刻や設定自体の不正は、環境由来の位置なしと区別して RangeError にする。

## 実行した Red → Green → Refactor

下表は実際に実行した結果である。既に成功するテストを、後から Red だったことにしていない。

| 段階 | コマンド | 実際の結果と変更 |
| --- | --- | --- |
| Red 1 | `npm test` | 1 件中 1 件失敗。初期 stub が point: null を返し、期待する (20, 80)、件数、MAD、古さと一致しなかった。 |
| Green 1 | `npm test` | 中央値と指標を実装し、1 件成功。 |
| Red 2 | `npm test` | 5 件中 4 件失敗。時間窓外、押下後に完了、別の文脈・モデル、無効値をサンプル件数に含めていた。 |
| Green 2 | `npm run check` | 入力の選別を追加し、型検査と 5 件成功。 |
| Red 3 | `npm test` | 17 件中 7 件失敗。件数不足時の指標、古いデータ・無効文脈の理由、両軸の分散超過、不正設定の例外が未実装だった。偶数件の中央値など、既に通る追加例も区別した。 |
| Green 3 | `npm run check` | 理由判定、閾値判定、設定検証を実装し、型検査と 17 件成功。 |
| Refactor | `npm run check` | 入力検証を分離し、有効サンプルを型ガードで表して座標の non-null assertion を除去。型検査と 17 件成功。 |

期待値は人工データから独立に定めた。たとえば、(30, 80)、(10, 100)、(20, 60) の座標ごとの中央値は (20, 80)、絶対偏差の中央値は (10, 20) になる。40 の境界では有効、50 の MAD では無効という結果を確かめた。

確認用の `npm check` という誤入力は npm の未知コマンドとして失敗し、`npm run check` に直した。この操作ミスは上表の振る舞いの Red に数えない。

## 実行環境と CI

Node.js 24.19.0、npm 11.9.0、TypeScript 5.9.3、@types/node 24.13.3 を使用した。依存は package-lock.json に固定している。製品の実行時依存はまだない。

今回の純粋ロジックには Node 標準の test runner を使う。追加の変換器やテストランナーを入れず TypeScript のテストを実行できるためであり、UI やブラウザを模擬するための選定ではない。Node の型除去は型検査をしないため、`tsc --noEmit` を別に実行する。[Node.js の TypeScript 説明](https://nodejs.org/api/typescript.html)

GitHub Actions の `CI` / `Core checks` は、すべての PR と `develop` / `main` の更新で `npm ci` と `npm run check` を実行する。Actions の参照もコミットで固定する。CI の有無だけで保護設定が有効になったとは扱わない。実際の実行結果は各 PR の Checks で確認する。

カメラ、MediaPipe、ブラウザ画面、モデル学習、Web 配布物のビルドはこのテストの対象外。Windows / Chrome / Vivaldi の確認と本人の視線精度測定もまだ行っていない。
